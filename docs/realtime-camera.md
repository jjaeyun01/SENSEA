# 실시간 카메라 처리와 메모리 제한

[모바일 앱](../mobile/README.md)은 Android와 iPhone의 실제 후면 카메라를 VisionCamera 5로 연결합니다. 모델과 프레임 변환은 카메라 전용 네이티브 스레드의 worklet에서 실행하고, UI에는 작은 결과만 전달합니다.

## 미리보기 우선 시작 (v0.4.1)

카메라 버튼 → 최초 안내의 시작 버튼 → OS 카메라 권한 → 후면 카메라와 미리보기 출력 연결 순서로 시작합니다. 비동기 장치 목록 조회가 끝나지 않았다는 이유로 버튼 동작을 중단하지 않습니다. NativePreviewView의 첫 영상 콜백이 도착해야 켜짐으로 표시하며, 12초 동안 영상이 없으면 오류를 표시하고 정리합니다.

모델 로드·프레임 변환·worklet 준비는 첫 미리보기 이후에 실행합니다. iOS GPU 변환이 지원되지 않거나 분석 준비에 실패하면 분석 상태에 이유를 표시하고 일반 미리보기를 유지합니다. 분석 출력을 함께 연결하는 데 실패한 경우에도 미리보기만 다시 연결합니다. 분석 빈도 5Hz 제한은 미리보기 프레임 속도를 제한하지 않습니다.

## 실제 앱의 데이터 흐름

```text
후면 카메라 ────────────────────────── 네이티브 미리보기
  └─ FrameOutput (목표 640×480; Android RGBA, iOS YUV)
       ├─ 분석 중 도착: 네이티브에서 버림
       ├─ 200ms 이내 / UI 전달 대기 중: 즉시 해제
       └─ Android CPU 리사이저 / iOS GPU 리사이저 → 320×320 RGB uint8
            ├─ 로컬 노출·세부 정보 검사
            └─ EfficientDet Lite0 CPU 추론
                 └─ 최대 25개 객체 메타데이터 → 레터박스 좌표 보정
                      └─ 최대 12개 객체 × 최근 4개 관찰 → 최대 3개 주의 후보
                           └─ 화면 / 최신 대기 음성 1개 (일반 객체 표시는 최대 5개)
```

앱은 사진 파일이나 base64를 생성하지 않고 서버에 프레임을 업로드하지 않습니다. 기존 정지 사진 설명 API는 이 실시간 루프에 연결하지 않았습니다.

## Android CPU 입력과 회전 (v0.4.3)

Android는 CameraX가 제공하는 `pixelFormat: "rgb"` RGBA 입력을 읽습니다. PRIVATE 형식의 장치 지원 실패와 YUV AHardwareBuffer의 Vulkan 가져오기 실패를 실제 실행에서 확인하여 Android 분석의 GPU 의존성을 제거했습니다. iOS는 기존 YUV·GPU 리사이저 설정을 유지합니다.

CPU 리사이저는 카메라 원본 전체를 복사하지 않고 단일 RGBA plane의 빌린 ByteBuffer에서 필요한 픽셀을 읽어 320×320 RGB 버퍼 하나에 기록합니다. 일반 frame.getPixelBuffer()의 HardwareBuffer 잠금 경로를 거치지 않습니다. 이 307,200바이트 버퍼는 세션 시작 시 한 번 만들고 프레임마다 재사용합니다. 행 간격과 패딩을 확인하고, 방향·미러 정보를 적용하며, 비율을 유지한 최근접 축소와 검은 여백을 사용합니다. Android CPU 물리 회전은 끄고 리사이저가 방향을 적용합니다. 품질 검사는 회전된 내용의 너비·높이를 사용하여 레터박스를 제외합니다.

Android 센서 방향은 CameraX의 회전 계약을 기준으로 처리합니다. VisionCamera 5.2.3의 `left` 메타데이터에는 시계방향 90도, `right`에는 270도를 적용합니다. [ImageInfo 공식 설명](https://developer.android.com/reference/androidx/camera/core/ImageInfo#getRotationDegrees())과 네이티브 매핑을 대조하고 비대칭 색상 입력의 네 방향 기대 행렬을 독립 테스트로 검증합니다.

실제 추론과 결과 디코딩을 마친 최신 결과가 처음 전달될 때 세션당 한 번 성공 로그를 기록합니다. 프레임 처리 실패 원인은 길이를 제한한 메시지 한 번만 기록하며 픽셀이나 프레임 객체를 로그에 넣지 않습니다. 미리보기와 모델 로딩만으로 성공 판정하지 않고, 모든 재시작에서 새 추론 결과가 도착해야 카메라 실행 검사를 통과합니다.

## Android CPU 추론 가속과 대체 실행 (v0.4.3)

Android의 기본 CPU 모델 로딩에는 XNNPACK delegate를 명시적으로 연결하고 스레드를 2개로 제한합니다. 모델의 8비트 입력·연산을 위해 QS8·QU8 플래그를 유지하며, interpreter의 CPU 스레드 수도 2개로 설정합니다. 모델 생성이나 텐서 할당 단계에서 가속 경로를 사용할 수 없으면 기존 CPU 경로로 다시 준비합니다. 실행 중 delegate 오류가 발생했을 때도 LiteRT의 CPU 재시도 기능을 사용하며, 재시도가 성공해 출력이 유효한 상태만 성공으로 처리합니다. 다른 실행 오류는 계속 분석 실패로 처리합니다. 이 대체 경로에도 1초 결과 유효시간을 적용합니다.

이 변경은 `react-native-fast-tflite` 3.0.1의 Android 기본 CPU 호출에만 적용합니다. `npm install`/`npm ci`의 postinstall 스크립트가 패키지 버전, 원본·수정본 C++ 소스의 LF 정규화 SHA-256, 추가 헤더의 SHA-256을 확인합니다. 의존성 소스가 예상과 다르면 패치를 중단하므로 라이브러리를 올릴 때 재검토해야 합니다. iOS와 명시적인 GPU·NNAPI 요청 경로는 유지합니다. delegate는 interpreter보다 늦게 해제하며, 생성·할당 실패 시에도 같은 순서를 지킵니다. 모델 가중치 캐시 파일이나 카메라 이미지 파일은 만들지 않습니다.

헤더는 공개 [LiteRT v1.4.0의 XNNPACK 헤더](https://github.com/google-ai-edge/LiteRT/blob/0348ffbe4232df35ab2651e6383528b3d8bf792f/tflite/delegates/xnnpack/xnnpack_delegate.h)를 고정 커밋에서 그대로 가져왔고 Apache-2.0 고지와 원문 LICENSE를 보관합니다. 현재 사용하는 LiteRT 1.4.0 바이너리와 맞는 구조체 크기·필드 위치를 컴파일 시 확인하므로 최신 헤더로 임의 교체하지 않습니다. 패치·소유권·출처는 [네이티브 변경 설명](../mobile/native/tflite-cpu/README.md)에 기록했습니다.

개발 중 RGBA plane 직접 읽기 이후에도 가속 전 에뮬레이터 처리에 약 9초가 걸려 결과가 폐기되는 실패를 확인했습니다. 당시 v0.4.3 XNNPACK 반영 APK의 1초 이내 결과 전달 검사는 실패했습니다. 이후 v0.4.4에서 시험 환경을 바꿔 확인한 결과와 비교 한계는 문서 끝에 기록합니다. 2개 스레드 설정이나 패치 적용 자체를 실시간 성능 검증으로 보지 않습니다.

## 제한과 소유권

| 항목 | 현재 설정 |
| --- | --- |
| 분석 시작 | 최소 200ms 간격, 최대 5Hz |
| 추론 동시 실행 | 1개 |
| 앱의 대기 프레임 큐 | 없음; 처리 중 유입은 네이티브에서 드롭 |
| JS 결과 전달 대기 | 최대 1개; UI가 받기 전에는 새 추론을 건너뜀 |
| 요청 카메라 해상도 | 640×480; 실제 선택이 1280×720 픽셀 수 초과면 중지 |
| 모델 입력 | RGB uint8 320×320 = 307,200바이트 |
| 모델 출력 | 위험 분석 경로에 최대 25개 후보; 일반 객체 표시는 최대 5개 |
| 추적 이력 | 최대 12개 객체 × 최근 4개 관찰, 이미지 없이 박스·점수·시각 등만 보관 |
| 주의 후보 | 최대 3개 |
| 결과 유효 시간 | 카메라 콜백 시작부터 1초 |
| 지속적인 처리 지연 | 1초를 초과한 결과가 연속 3개면 분석 중지·미리보기 유지 |
| 자동 음성 | 최신 대기 발화 1개; 일반 주의 최소 4초·동일 주의 8초, 우선순위 상승 별도 1.5초 제한 |

`createNativeSession.ts`가 VisionCamera의 `dropFramesWhileBusy: true`를 설정합니다. JS에서 늦게 버리는 것만으로는 네이티브 큐 증가를 막을 수 없으므로 입력 단계부터 제한합니다.

`analyzeOwnedFrame`은 성공·오류·스킵 모두 원본 프레임을 한 번 반환합니다. Android의 모델 입력 버퍼는 같은 스레드에서 추론이 끝난 후에만 다시 씁니다. iOS 변환 버퍼는 빌린 메모리이므로 모델 실행이 끝나기 전에 해제하지 않습니다. `finally`에서 iOS 변환 버퍼를 먼저 해제하고, 두 플랫폼 모두 원본 프레임을 반환합니다. 이미지 배열이나 영상 이력을 보관하지 않습니다. v0.4.4의 위험 요소 추적기는 작은 탐지 메타데이터만 최대 12개 객체 × 최근 4개 관찰로 제한해 보관하고, 종료·오류·만료 시 초기화합니다.

위 숫자는 전체 앱 메모리 상한이 아닙니다. OS 카메라 풀, 미리보기, GPU 리사이저, 모델 텐서와 네이티브 라이브러리 할당은 별도로 존재하며 실기기 측정이 필요합니다. 5Hz도 상한일 뿐 기기에서 보장되는 속도가 아닙니다.

## 종료와 오류

카메라 끄기·앱 백그라운드·카메라 인터럽트는 먼저 입력과 음성을 중지합니다. 카메라 시작 작업을 기다린 뒤 stop()과 configure([])로 장치 입력·출력을 분리합니다. 진행 중 추론이 끝나면 같은 스레드에서 콜백을 해제하고 모델·변환기·미리보기를 정리합니다. 분석용 프레임 출력·worklet 런타임·카메라 세션 객체는 앱 수명 동안 한 세트만 재사용합니다. VisionCamera 5.2.3의 Android 출력 dispose는 executor를 종료하지 않으므로, 화면을 열 때마다 새 스레드를 만들지 않기 위한 선택입니다. 카메라가 꺼져 있을 때는 장치가 분리되어 있고 프레임 콜백도 없습니다. 정리가 끝나기 전에는 두 번째 모델을 로드하지 않습니다.

동기 네이티브 추론을 JS 타이머로 강제 종료하거나, 사용 중 버퍼를 먼저 해제하지 않습니다. 추론이 멈춘 경우 새 입력은 계속 버리고 재진입을 막습니다. 네이티브 자원 반환이 실패하면 재할당을 차단하고 앱 재실행을 안내합니다. 실기기에서 드라이버 중단·오류도 확인해야 합니다.

분석 결과의 처리 시간이 1초를 넘으면 UI에 전달하지 않습니다. 처음 준비할 때의 단발 지연은 허용하되, 연속 3개 결과가 기한을 넘으면 분석을 중지하고 화면에 이유를 알리며 미리보기는 유지합니다. 기한 내 결과가 나오면 연속 초과 횟수를 0으로 초기화합니다. 중지 이후 프레임은 추론을 건너뛰고 반환하며, 사용자가 카메라를 다시 시작해야 분석을 재시도합니다. 가상 시계 테스트로 1000ms 경계, 연속 횟수 초기화, 오래된 결과 미전달, 기존 200ms 간격과 UI 전달 대기 1개 제한을 확인합니다.

모델을 로딩하는 중 끄더라도 카메라 장치는 먼저 정지·분리하고, 로딩이 끝나면 모델 자원을 반환합니다. UI에서 늦게 도착한 결과는 버리고, 갱신되지 않은 결과는 1초 후 표시·추적 근거·앱 안의 대기 음성을 지웁니다. 이미 Android TalkBack에 전달한 접근성 발화는 앱의 TTS 중지로 강제 취소할 수 없습니다. 앱 복귀 후에는 사용자가 카메라를 다시 켭니다.

## 검증과 남은 범위

v0.4.4 소스의 Node 테스트 162개와 TypeScript 검사가 통과했습니다. 검사는 1만 프레임 스킵, 오류 경로, 빌린 메모리의 사용 순서와 해제, 출력 크기·유효 값, 레터박스 좌표, 제한된 객체 추적, 관찰 시간·모호한 대응·장면 이동, 음성 우선순위·중복 제한·비동기 취소를 다룹니다. CI는 실제 배포 모델을 로드해 합성 픽셀로 추론하고 출력 계약을 확인하며, 두 플랫폼 번들과 네이티브 앱을 컴파일합니다.

Android 증분 빌드에서 `.mjs`만 수정했을 때 Gradle이 이전 Hermes 번들을 재사용하는 문제도 수정했습니다. [Expo config plugin](../mobile/plugins/with-mjs-bundle-inputs.js)이 `BundleHermesCTask`의 입력에 `**/*.mjs`를 등록하며, prebuild를 다시 실행해도 중복 등록하지 않습니다. JS 처리 코드가 바뀌면 APK에 새 번들이 들어가도록 하는 빌드 수정이며, 네이티브 추론 성능의 성공 판정과는 별개입니다.

Android/iPhone 실기기의 장시간 메모리·GPU 풀·발열·배터리·인식 지연은 아직 측정하지 않았습니다. v0.4.4는 영상상 위험 요소의 주의 규칙을 구현했으며 실제 위험 경고 정확도는 검증하지 않았습니다. 차도/인도 영역 분할, 계단·낙차·포트홀 인식, 실제 거리·충돌 확률·TTC 계산은 구현하지 않았습니다. 객체를 찾지 못한 경우에도 이동 가능이나 안전한 경로로 표현하지 않습니다.

## 기존 공용 모듈

`mobile/vision/RealtimeFrameProcessor.mjs`는 소유권 있는 Y8 입력을 받는 별도 참조 모듈로 남겼습니다. 이 모듈은 활성 1장 + 최신 대기 1장, 입력당 backing buffer 512KiB, 시간 초과 후 중지 정책을 갖습니다. 실제 네이티브 앱은 복사와 JS 대기를 줄이기 위해 위의 직접 worklet 경로를 사용합니다. 두 경로의 메모리·시간 제한을 혼동하지 않습니다.

공개 API 자료: [VisionCamera frame output](https://visioncamera.margelo.com/docs/frame-output), [네이티브 프레임 플러그인](https://visioncamera.margelo.com/docs/native-frame-processor-plugins), [react-native-fast-tflite](https://github.com/margelo/react-native-fast-tflite). 회사 프로젝트 소스나 내부 자료를 가져오지 않았습니다.

## v0.4.3 로컬 APK 실행 한계 (2026-09-27)

APK 정적 검사와 설치는 완료했지만 에뮬레이터의 카메라 동시 실행에서 첫 처리 약 4.5초가 측정되어 엄격한 1초 실시간 검사는 실패했습니다. 연속 지연 후 분석 중단 안내가 표시되고 미리보기는 유지됩니다. 같은 모델의 독립 실행은 약 20~32ms이며 카메라를 켜면 독립 실행도 최대 약 3.4초로 느려져 가상 카메라 렌더링 동시 부하의 영향이 확인됐습니다. 실제 휴대폰의 인식 속도와 지속 동작은 아직 검증하지 않았습니다.

사용자 요청으로 이 상태의 설치 시험 APK를 먼저 전달합니다. 4초 지연 허용 요청이 4GB의 메모리 상한 설정이나 오래된 인식 결과의 안내 허용으로 자동 변환되지는 않습니다. 기존 버퍼 제한·1초 결과 만료·3회 연속 초과 시 분석 중지는 유지합니다. 메모리의 관측값과 검사 범위는 README1 최종 전달 기록을 확인하세요.

## v0.4.4 위험 요소 관찰 연결 (2026-09-27)

사용자의 우선순위에 따라 경로 기능보다 먼저 카메라의 주의 정보를 앱 화면과 음성에 연결했습니다. 단일 탐지가 아니라 최소 2개 관찰·180ms의 반복 근거를 확인하며, 영상 크기 증가에는 최소 3개 관찰·400ms와 형태·점수·면적 변화 조건을 적용합니다. 모호한 추적, 잘린 박스, 장면 전체 움직임에서는 변화 근거를 억제합니다. 임계값은 실측 보정 전의 초기값이며 실제 물체의 접근이나 충돌을 확정하지 않습니다.

프레임 유효시간은 계속 콜백 시작부터 1초입니다. 주의 음성이 일반 음성 뒤에 쌓이지 않도록 최신 대기 발화 하나를 유지하고 실제 발화 직전에 다시 신선도를 확인합니다. 만료·음소거·취소로 발화를 버렸다면 해당 경고의 예약을 복원해 새 유효 결과를 다시 알릴 수 있게 했습니다. 새 경고의 예약이 이전 취소 콜백에 지워지지 않도록 별도 세대 번호를 사용합니다. 일반 객체·영상 품질 안내에도 별도 세대 번호와 미전달 복원을 적용하여 비동기 음성 중지 지연이나 실패 후 같은 안내를 다시 시도할 수 있게 했습니다.

v0.4.4 APK의 정적 검사와 에뮬레이터 3세션의 최신 추론·5초 이후 유지·중지/재시작·앱 전환 검사를 통과했습니다. 새 위험 요소 카드의 연속 관찰 상태도 확인했습니다. 세션별 첫 처리는 245/208/346ms, 검사 중 1회 PSS는 195.8MiB/RSS는 322.0MiB였습니다. 전체 지연 분포나 메모리 최대값이 아닙니다. 이번에는 4코어·host GPU·720×1600 가상 카메라를 사용했으며 이전 v0.4.3의 2코어·SwiftShader와 달라 직접 성능 비교할 수 없습니다. 실제 위험 사건의 정밀도·재현율, 실폰 성능과 TalkBack 실행은 아직 검증하지 않았습니다. 상세 알고리즘·지원 대상·평가 계획은 [위험 요소 관찰](hazard-awareness.md), 최종 설치 파일·시험 조건·원본 근거는 [README1](../README1.md)에 기록했습니다.
