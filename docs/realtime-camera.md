# 실시간 카메라 처리와 메모리 제한

카메라 미리보기와 분석 속도를 분리합니다. 미리보기는 기기에서 자연스럽게 표시하고, 분석은 작은 프레임을 제한된 속도로 처리합니다. 모든 프레임을 서버에 보내거나 촬영 파일을 계속 생성하지 않습니다.

현재 구현은 프레임 처리 모듈과 로컬 사진 품질 분석기입니다. 실제 카메라의 네이티브 버퍼 어댑터, Expo 화면, 객체 탐지·차도/인도 분할 모델은 아직 연결하지 않았습니다. 실시간 품질 검사 기반을 구현한 것이며 실시간 위험물 인식을 완성한 상태는 아닙니다.

## 데이터 흐름

```text
카메라 미리보기
  └─ 네이티브에서 작은 Y8 프레임 추출·샘플링
       └─ RealtimeFrameProcessor
            ├─ 분석 중: 1장
            ├─ 대기: 최신 1장 (교체되는 이전 프레임 즉시 해제)
            └─ analyzeLumaFrame → 작은 품질 결과만 UI로 전달

사용자의 상세 설명 요청 (정지 확인)
  └─ LatestVisionController → /vision/describe → 최신 결과만 음성 출력
```

서버 모델 호출은 기존처럼 별도 요청이며 기본 분당 6회 제한을 유지합니다. 로컬 프레임 처리 루프는 HTTP나 TTS를 자동 호출하지 않습니다. 로컬 결과는 매 프레임 낭독하지 말고, 실제 앱에서 같은 안내의 반복과 길안내 음성의 충돌을 조정해야 합니다.

## 기본 설정

| 항목 | 설정 | 의미 |
| --- | --- | --- |
| 분석 시작 간격 | 최소 200ms | 최대 초당 5회, 처리 속도가 느리면 더 낮아짐 |
| 대기열 | 최신 프레임 1장 | 분석 중 1장을 포함해 최대 2장 유지 |
| 프레임 크기 상한 | backing buffer 512KiB | 작은 view로 큰 원본 버퍼를 붙잡는 경우도 거부 |
| 분석 입력 보관 상한 | 최대 1MiB | 이 처리기가 보유한 활성·대기 입력 버퍼만의 상한 |
| 결과 유효 시간 | 촬영 후 1초 | 오래된 결과와 오래된 대기 프레임 폐기 |
| 분석 시간 제한 | 1.5초 | 취소 요청 후 입력 중지, 자동 재시작하지 않음 |
| 권장 최초 입력 | 320×240 Y8 | 패딩이 없다면 장당 76,800바이트 |

숫자는 실기기 평가를 위한 초기 설정입니다. 기기 발열·배터리·카메라 미리보기 성능을 측정해 조정해야 합니다. 1MiB는 앱 전체 메모리 상한이 아닙니다. 카메라 드라이버, 미리보기, 네이티브 어댑터의 순간 할당, 모델 텐서, UI가 따로 사용하는 메모리는 포함하지 않습니다.

## 모듈 연결

```js
import { RealtimeFrameProcessor } from "./vision/RealtimeFrameProcessor.mjs";
import { analyzeLumaFrame } from "./vision/analyzeLumaFrame.mjs";

const realtime = new RealtimeFrameProcessor({
  analyze: analyzeLumaFrame,
  onResult: (quality, timing) => updateQualityIndicator(quality, timing),
  onError: error => showAccessibleError(error.message),
});

// 카메라 권한이 있고 화면이 활성 상태일 때:
realtime.start();

// 아래 함수는 앞으로 구현할 네이티브 카메라 어댑터에서 호출합니다.
// frame은 독립적으로 소유한 작은 Y8 버퍼와 release()를 제공해야 합니다.
function onOwnedLumaFrame(frame) {
  realtime.offer(frame); // true/false 모두 소유권을 넘김. 호출자가 다시 release하지 않음.
}

// 백그라운드 또는 화면 이탈:
realtime.pause(); // 네이티브 프레임 공급도 함께 중단

// 화면 해제:
realtime.dispose();
```

`frame` 계약:

- `data: Uint8Array`: 한 픽셀당 1바이트의 밝기 값. 선택적으로 행 끝 패딩 허용.
- `width, height, rowStride?`: 픽셀 단위 크기와 행의 바이트 간격. 생략하면 rowStride=width.
- `capturedAt`: 처리기의 `performance.now()`와 같은 기준의 단조 증가 밀리초 시각. 다른 원점의 네이티브 timestamp를 그대로 전달하지 않습니다.
- `release()`: 버퍼 대여를 끝내는 동기 함수. 제출한 프레임 객체는 다시 제출하지 않습니다.

반환값 false는 분석하지 않고 해제했음을 의미합니다. 유효하지 않은 프레임 형식도 release 함수가 있는 한 정리합니다. 동일 객체의 중복 제출과 release 누락은 계약 오류로 예외가 발생하며, 그때는 새 소유권을 받지 않습니다.

## 네이티브 연결 시 필요한 조건

카메라 콜백이 끝나면 유효하지 않게 되는 프레임 핸들을 JS 비동기 대기열에 넣지 않습니다. 네이티브 계층에서 생존 기간이 보장되는 작은 버퍼를 소유하거나 복사한 뒤 전달하고, `release`와 네이티브 자원 반환을 연결해야 합니다. 처리 중인 버퍼를 다른 프레임용으로 덮어쓰면 안 됩니다.

원본 고해상도 RGBA·base64를 먼저 JS로 옮겨서 줄이지 말고, 네이티브에서 샘플링과 축소를 수행합니다. 어댑터와 카메라 드라이버 자체의 대기열도 제한해야 합니다. JS 처리기만으로 상위 계층의 무한 큐를 해결할 수는 없습니다.

[CameraX 공식 문서](https://developer.android.com/media/camera/camerax/analyze)는 최신 프레임을 유지하는 비차단 분석 방식과 분석 후 ImageProxy 해제를 설명합니다. 이 동작 원칙을 참고했으며 회사 프로젝트 구현이나 공식 예제 코드를 복사하지 않았습니다. [ML Kit 실시간 객체 분석 안내](https://developers.google.com/ml-kit/vision/object-detection/android)도 스트림 처리와 입력 속도 제한을 검토할 때 참고할 수 있습니다. 구체적인 객체·도로 분할 모델은 별도로 선정·검증해야 합니다.

현재 `expo-camera.takePictureAsync`를 짧은 setInterval로 반복하는 방식은 연결하지 않았습니다. [Expo Camera 문서](https://docs.expo.dev/versions/latest/sdk/camera/)에서 촬영 API와 생명주기를 확인하고, 원시 프레임 처리를 지원할 네이티브 모듈은 Expo 개발 빌드와 실제 기기에서 검증한 뒤 연결해야 합니다.

## 취소와 자원 해제

대기 프레임은 교체·정지·종료 시 즉시 해제합니다. 분석 중인 프레임은 취소 신호를 보내더라도 분석 함수가 끝나기 전에는 해제하지 않습니다. 해제를 먼저 하면 네이티브 코드가 이미 반환된 메모리를 읽을 수 있기 때문입니다.

분석이 응답하지 않으면 입력을 멈추고 활성 버퍼 1장을 보관한 채 작업 종료를 기다립니다. 이 동안 새 분석을 겹쳐 시작하지 않습니다. 네이티브 worker 종료·취소 완료를 보장한 후 작업이 끝나도록 어댑터를 구현해야 합니다. release 실패 시에도 입력을 중지하며 어댑터 측 자원 복구가 필요합니다.

JS의 타이머는 동기적으로 멈춰 있는 JS 실행을 선점할 수 없습니다. 무거운 모델은 네이티브 worker에서 실행하고, 이 JS 모듈은 작은 품질 검사나 비동기 worker의 조정 용도로 사용합니다.

새 프레임이 도착했다는 이유만으로 분석 중이던 모든 결과를 버리지는 않습니다. 그렇게 하면 카메라가 분석보다 빠를 때 결과가 영원히 나오지 않을 수 있습니다. 분석은 한 번에 하나씩 수행하므로 결과 순서가 뒤바뀌지 않으며, 같은 세션에서 1초 이내인 완료 결과만 전달합니다. 화면 종료·세션 변경·시간 초과 후의 결과는 전달하지 않습니다.

## 로컬 품질 검사와 검증 범위

`analyzeLumaFrame`은 회색조 샘플의 어두운/밝은 픽셀 비율과 인접 샘플의 밝기 차이를 검사합니다. 별도의 이미지 복사·전체 히스토그램·사진 기록 없이 스칼라 통계를 반환합니다. 단색 장면과 흐린 장면은 구분하지 못하며, 이 결과는 보행 허가나 인식 정확도 점수가 아닙니다. 서버 Pillow 검사와는 입력 해상도와 세부 정보 지표가 달라 결과가 같다고 가정하지 않습니다.

Node 테스트는 1만 프레임 유입 시 최대 두 입력만 보관하는지, 해제 콜백이 한 번씩 실행되는지, 느린 분석·시간 초과·앱 종료·재시작·잘못된 큰 버퍼·오류 후 정리가 올바른지 검증합니다. 실제 휴대폰의 RSS, GPU 메모리, 네이티브 풀, 발열, 배터리, 장시간 실행 누수는 아직 측정하지 않았습니다.
